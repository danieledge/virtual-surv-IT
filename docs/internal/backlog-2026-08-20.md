# Backlog - parked with reasons (2026-08-20)

Two items parked deliberately, each with what is done, what is not, and what would have to
be true to pick it up. Neither is blocked on effort alone; both are blocked on a decision.

## 1. Model-runtime boundary / CLI independence

**Status:** POC complete and proved, **local branch only** (`poc/runtime-boundary`).
**Not on the remote by owner decision** - the GitHub repo is public and this is
architecture exploration, so the branch was pushed, then deleted from `origin`. The local
branch holds both commits; re-push if that changes. Report:
`docs/internal/poc-runtime-boundary.md`.

**What is proved.** virt-surv can own the boundary: the agent loop, the tool decisions,
the turn limit and the accounting are ours, and the provider is interchangeable. The same
workflow runs unchanged against an offline scripted runtime **and** against the real
headless CLI (3 turns, 2 tool calls, ~36s, a genuine model critique). 16 tests, no
credentials, no network.

**What is NOT proved, and the honest proportion.** The POC is ~500 lines: one workflow,
one agent, two tools. The framework is 27 skills, 13 agents, ~2,470 tests, three guard
hooks, the DoD gate, evidence, state, MCP. Missing entirely: skill loading, subagent
dispatch, per-agent tool grants, human gates (`AskUserQuestion`), engagement state, the DoD
gate, evidence packs, MCP/Jira, streaming, retries, compaction, prompt caching, resume.

**The split that decides the effort.** The missing pieces are not one problem:

- **Ours, and portable** - skills are file reads, state is `engagement_state.py`, the gate
  is `check_artifacts.py`, evidence is a renderer. These carry across largely unchanged.
- **The harness's, and a project** - the tool-execution loop with its permission UI,
  compaction, MCP client, streaming, session management, subagent orchestration.
  Replicating this is not "finish the POC", it is building an agent harness. **The three
  guard hooks live inside that lifecycle**, which is why re-homing them is the hardest
  unsolved piece.

**The decision that unblocks it - and it is not a build decision.** Two different problems
get conflated:

1. *"Claude Code can't run on-prem"* → the harness must be replaced. Big project; this POC
   is the right starting point.
2. *"Claude Code runs, but must talk to an internal endpoint"* → keep the harness and point
   it at that endpoint. Almost none of this work is needed.

**Establish which problem is real before building further.** If (2), park this
permanently. If (1), the cheapest next step is one adapter against the approved internal
SDK, re-running the POC's existing tests - that converts the largest unknown (does a real
non-Claude provider parse and drive the loop?) into a fact for a day's work.

**Known live findings worth keeping** (both cost real time to discover):
- `claude -p` blocks ~3s on inherited stdin; the adapter closes it (`DEVNULL`).
- An `ANTHROPIC_API_KEY` **takes precedence over a claude.ai login**, so a credit-less key
  silently shadows a working subscription ("Credit balance is too low"). The adapter drops
  that variable from the child environment only.

## 2. TUI framework for `virt-surv go`

**Status:** raised 2026-08-19 ("make it more like an app - area borders, better UI"), not
started. The current screen was reworked instead (wordmark, grouped actions, spacing,
Morgan asking the question) and is committed on `dev`.

**The question:** move the launcher to a real TUI framework (Textual being the obvious
candidate) rather than hand-printed lines plus the `prompt_toolkit` picker.

**What it would buy:** genuine layout - panels with borders, side-by-side regions, a
scrollable engagement list, live-updating status, mouse support, focus handling, and
consistent theming rather than two tiers that must be kept in visual sync by hand (a real
defect this week: the redesign only reached the numbered tier, and the picker tier - the
one actually seen - kept the old rows until a screenshot exposed it).

**What it would cost, and why it is not obvious:**

- **A hard dependency.** The launcher is stdlib-plus-optional-`rich` today and must run on
  locked-down corporate Windows where installs are the constraint. Textual pulls a real
  dependency tree into the one component that must work before anything else does.
- **The stdout contract.** `virt-surv go` prints the decision to **stdout** and everything
  else to stderr, because a shell function captures it (`$(...)`). A full-screen TUI takes
  over the terminal; the decision-capture contract needs re-proving, and it has already
  produced one live bug (`input()` leaking its prompt onto stdout).
- **cp1252 consoles.** Box-drawing and emoji already degrade deliberately; a framework's
  defaults must be forced down the same path.
- **The fallback tier stays.** Where the framework can't run, the numbered flow is still
  needed - so this replaces one of two tiers, it does not remove the second.

**Recommendation:** worth doing **only if** the launcher grows genuinely
app-like requirements (live progress during an engagement, a dashboard view, browsing many
engagements). For a launch screen answering one question, the current version is
proportionate. Revisit if the Control Tower idea (live engagement view) is ever taken up -
that is the use case that would actually justify the dependency, and it should be decided
together with this, not separately.

## 3. `[n]` new engagement: take the request up front, and offer unattended

**Raised:** 2026-08-24 by the owner. **Status:** not started.

Today `[n]` launches Claude with `--new` and nothing else, so the first thing that happens
in-session is Morgan asking what the work is. Two capabilities the Jira route already has
are missing from the one people use most:

1. **Type the request at the launcher.** The human is already at a keyboard with a screen
   in front of them. Collecting the request there and pre-seeding it removes a whole
   question-and-answer round trip from the session, exactly as `[j]` does with a ticket
   reference.
2. **Offer unattended.** `--auto` is currently reachable only from a Jira ticket, which is
   an accident of where it was built rather than a property of autonomy. A typed request is
   just as capable of being worked end to end without questions, and the pre-flight
   authorisation screen already exists and is source-agnostic.

**Shape it would take.** A prompt screen behind `[n]`, same framed shell as `jira_screen`:
free-text request, `Ctrl-A` to toggle unattended, Enter to start, Esc for today's plain
`--new`. Unattended reuses `auto_preflight_screen` unchanged, and the decision becomes
`/engage --new --request "<text>"` (plus `--auto`). Everything downstream - the assumption
ledger, park-don't-guess, the always-PARTIAL close, the AUTO-* gates - is already
source-agnostic and needs no change.

**Worth deciding before building:** whether a typed request should keep the plain `--new`
path as the default Enter action (it should - typing is an offer, never a toll gate), and
how a long multi-line request is entered in a single-line field. The existing ticket field
is deliberately one line; a request may not be.

## 4. Truly headless (`claude -p`) runs

**Raised:** 2026-08-24 by the owner. **Status:** researched, not started. Do AFTER the
enforcement inventory - running unattended work through a pipeline multiplies whatever is
wrong with the gates, and this week proved the gates can be dead without anyone noticing.

**It is possible, and closer than expected.** Anthropic support four routes: `claude -p`
driving the CLI as a subprocess (their recommendation for any language that is not
Python/TypeScript), the Agent SDK as a library, hosted Managed Agents, and their own GitHub
Actions / GitLab CI integrations. Example code: `github.com/anthropics/claude-agent-sdk-demos`.

**The shape for us** is `claude -p "/engage --new --jira SURV-1 --auto" --permission-mode
dontAsk` plus allow rules for the team scripts, with `--output-format json` for a pipeline to
branch on, and `system/init`'s `plugin_errors` / `mcp_server_errors` to fail the run when the
plugin or an MCP server did not load.

**Four findings that decide the design:**

1. **Only `--auto` can run headless.** `-p` starts in Manual permission mode, and the
   recommended CI mode `dontAsk` **denies `AskUserQuestion` even when an allow rule matches**.
   Our whole opening gate is an AskUserQuestion batch, so a headless run of the normal flow
   does not degrade, it stalls. Autonomous mode is the enabling feature, not a nice-to-have.
2. **We must NOT use `--bare`**, although Anthropic recommend it for scripted calls and say it
   will become the `-p` default. It skips hooks, plugins, MCP, CLAUDE.md and auto-memory -
   for us that disables the entire team plugin and all three guard hooks. Running `-p`
   without it is a deliberate choice to document, not an oversight. Bonus: non-bare `-p` can
   use the subscription, while `--bare` demands `ANTHROPIC_API_KEY`.
3. **Execution consent still binds correctly.** There is no launcher TUI in a pipeline, so a
   headless run is static-only unless a human puts `CST_ALLOW_EXEC=1` in the CI configuration
   - itself a deliberate human act in a reviewed file, so ADR-002's property survives intact.
4. **It closes PARTIAL**, sign-off outstanding, clearable from `[s]` in the launcher.

**The real question is not technical.** Who is accountable for a run that parks at 3am, and
who reads the assumption ledger before the work is used? Wants an ADR, and the build should
be thin - a documented command that emits the right `claude -p` invocation, not a new
subsystem.

## 5. The task-panel nudge punishes the sessions that got it right

**Raised:** 2026-08-24 from a live corporate run. **Status:** diagnosed, not fixed.

Observed: the stop hook nudged `asam-aej-alert-analysis` to seed the task panel at phase
`delivery` - and the session answered "the task panel already has the gates seeded (tasks
1-5, one in_progress). Logging the note to suppress the repeat nudge." It had done the right
thing, was told off for not doing it, and spent a turn writing a suppression marker.

**The design is honest about what it cannot do** (`scripts/todo_panel_nudge.py`): TodoWrite
is model-invoked and its content is ephemeral, so no hook can verify the panel from outside
the turn. It can only nudge at a structurally chosen moment. That part is sound.

**The flaw is where the suppression marker comes from.** The only evidence the hook can see
is a `log-note "todo-panel-seeded"` entry, and today the model is told to write that *in
response to the nudge*. So a session that seeds the panel spontaneously - exactly what the
operating guide asks, "the moment the plan is agreed" - never writes the marker, and is
therefore guaranteed to be nudged later. The hook fires on everyone once, and correct
behaviour earns the same interruption as incorrect behaviour.

**A second, smaller mismatch:** it triggers when phase reaches `delivery`/`close`, but the
action it asks for is due at plan time. By delivery a compliant session seeded the panel long
ago, so the nudge is always late for the people who need it least.

**Fix, in order of value:**

1. **Make the marker a byproduct of doing it right, not of being corrected.** The operating
   guide should ask for the `log-note` in the same breath as seeding the panel. Then a
   compliant session self-suppresses before the hook ever runs, and the nudge reaches only
   sessions that genuinely skipped it - which is what it was built for.
2. Consider moving the trigger to the plan phase, so it lands when the action is due.
3. Leave the hook's logic alone otherwise - warn-first, once-per-engagement, fail-open and
   read-only are all correct, and it is a guard file, so any change is staged and
   human-applied.
