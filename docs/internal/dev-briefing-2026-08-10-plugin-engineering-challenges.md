# Building a Claude Code Plugin Like This One: A Technical Primer

This document is for the team building virt-survtecb (the compliance-surveillance-team plugin), not for its end users. The plugin's job sounds simple on paper: a handful of Python hooks that gate what an AI agent is allowed to read, write and execute. In practice it has surfaced a specific, recurring category of engineering problem that generic "AI agent tooling" advice doesn't prepare you for: **hooks that must run correctly, fast, and safely, on an OS you don't control, invoked by a process (the model) you don't fully control either.** What follows is five real incidents from this repo's own history, with file and line references, that show what that actually costs.

## 1. Cross-platform hook invocation is not a solved problem

`.claude/hooks/run-guard.sh` exists because a bare `python3` command, which works everywhere on Linux/macOS, simply does not exist on Windows (the interpreter there is `python` or the `py` launcher). That alone forces a portable launcher. But the launcher's own comments (lines 24-30) document something much stranger: on a Windows box where `python3.exe` resolves to the **App Execution Alias stub** (present to `command -v`, but not a real interpreter — it silently redirects to the Microsoft Store), actually *executing* it to version-probe triggers a multi-second Store redirect check, every time. A single `/engage` that looked like it was hanging for "several minutes" turned out to be that stub hang repeated dozens of times across one session, because five separate hooks each ran their own probe loop. The fix required separating cheap existence checks (`command -v`, safe to redo every call) from the expensive execution probe (must happen once, cached to `VSIT/local/guard-interpreter`, and trusted after) — plus an OS-aware probe order (`$OS = Windows_NT` tries `python`/`py` before the Store-stub-prone `python3` there, line 58-62) and a UTF-8 pin (`PYTHONIOENCODING`/`PYTHONUTF8`, lines 42-43) because native Windows Python decodes stdin/stdout using the console codepage, not UTF-8 — which silently mis-decodes non-ASCII in a way that doesn't raise, it just makes correct data compare unequal to a guard constant and trips a false block.

One more thing worth internalizing even though it's not in the script's own comments: Windows has no true POSIX `exec`. On Linux/macOS, `exec "$interpreter" "$@"` replaces the shell process in place — one process, total. Git Bash *emulates* `exec` on Windows by spawning a brand-new process and terminating the shell around it. So even the "fast, cached" path in `run-guard.sh` — cache hit, no probing, straight to `exec` — still costs two real Windows process-creation events, not one. That matters directly for the next section.

## 2. Process-spawn cost compounds with corporate endpoint security, and it's a recurring class, not a one-off

The clearest incident is documented in `scripts/bash_hook_dispatcher.py`'s module docstring (lines 1-25). Before this dispatcher existed, five separate hooks all matched `Bash` — `guard-raw-data`, `guard-code-execution`, `guard-consent-writes`, `document_input_redirect`, `module_form_redirect` — each wired as its own `hooks.json` entry, i.e. its own `sh run-guard.sh <script>` process. Even with the interpreter-resolution fixes from §1 already applied, that left five process-creation events per single Bash tool call. On a corporate Windows box where every new process gets scanned by endpoint security, that's five scans instead of one — confirmed live on 2026-07-31: **51 seconds for the step-0 probe alone, 1m31s for the very next Bash call, roughly two minutes total just to open an engagement**, even with every individual hang already fixed. The fix (P4) runs the same five checks unmodified, imported by file path rather than reimplemented, in one process, while carefully preserving each guard's own fail-open/fail-closed crash policy (see §4) and its original tool-matcher scope, since collapsing five processes into one must not silently widen or narrow which tool calls each check fires on.

This is not an isolated fix — it's a pattern that keeps reappearing wherever a per-call process-spawn cost meets a search/scan pattern that runs more often than intended. Three further instances, all found and fixed the same day (2026-08-10):

- **`_raw_data_present()`** in `.claude/hooks/guard-raw-data.py` (lines 147-165) did a full `os.walk()` over `data/raw/` to decide whether an ancestor-rooted search should be blocked. Because a path-less Grep or Glob search is rooted at the working directory by design, and the project root is trivially an ancestor of `data/raw/`, this walk ran on nearly every Grep/Glob call in a session, not just the rare ones that actually target raw data. Fixed with a short-TTL file cache (same pattern as `VSIT/local/guard-interpreter`), staged at `scripts/staged_hooks/guard-raw-data.py` pending human application (see §3).
- **`scripts/engagement_state.py`**'s command surface had no batch/multi-decision mode — a live bug report found the intake step chaining eight separate `python.exe` cold-starts in one Bash command to apply eight small state changes, one measured at 3816ms, one erroring outright. Fixed with a new `set-decisions --json '{...}'` batch subcommand: one process, one load/render cycle, for what used to be N of each.
- **Pip (`review-scorer`), the team's own haiku-tier context-detection helper**, was invoking `ls`/`cat` via Bash to explore directories and read files during its context-detection pass — a single chained `ls ... && ls ... && cat ... && cat ...` measured at 3555ms. This one wasn't a hook or guard problem at all (the guards fire once per Bash *call*, regardless of how many `&&`-chained commands are inside it) — it was the agent's own tool choice. `Read`/`Glob` do the identical job with zero subprocess spawns, on any platform. Fixed by tightening Pip's own agent instructions to require `Read`/`Glob` for anything that lists a directory or reads a file, reserving Bash for `git diff`/`git status` only.

The throughline across all four: on Windows, and especially on an AV-scanned corporate endpoint, every new process is expensive in a way that doesn't show up on a Linux dev laptop, and it multiplies with the number of hooks *and* the frequency of the operation that spawns them *and* which tool an agent chooses for a given job — not just with the size of the codebase.

## 3. "The human applies safety-critical changes" is a deliberate design pattern, not friction to route around

The model can *propose* a fix to a security guard, but it is mechanically blocked from writing directly to `.claude/hooks/**`, `hooks/hooks.json`, or `.claude/settings*.json` — enforced by `guard-consent-writes.py` itself (see its docstring: "BLOCK Write/Edit of the safety hooks themselves... a model that can edit a guard can neuter it"). The escape valve is `scripts/staged_hooks/` — an unguarded parallel directory holding proposed copies of every guard and launcher — plus a family of small `scripts/apply-*.sh` scripts (e.g. `apply-guard-raw-coverage.sh`, `apply-bash-hook-dispatcher.sh`, `apply-raw-data-present-cache.sh`) that a human runs to promote a staged file to its live location. The model can edit the staged copy freely; only a human can make it live.

`tests/test_hooks_in_sync.py::test_staged_matches_live` is the mechanism that makes this stick. It does a byte-for-byte comparison of every staged file against its live counterpart, and if they differ, **the test fails — it does not skip.** The docstring explains why that distinction was hard-won: an earlier audit found a guard had drifted from its staged copy while the full suite still reported green, because an earlier version of this same test called `pytest.skip()` on a mismatch instead of failing. That's the exact failure mode this whole domain exists to guard against, so now a pending fix fails the suite loudly until a human runs the apply script — proven live again today: the raw-data-cache fix above sits staged, and both `test_live_guard_matches_staged_once_applied` and `test_staged_matches_live[guard-raw-data.py]` fail on purpose right now, pointing at the exact command to run.

## 4. Fail-open vs fail-closed is chosen per guard, on purpose, not left to default behavior

Every guard in this repo makes an explicit, documented choice about what happens when something goes wrong, and the choices are not uniform. `guard-raw-data.py`'s presence/path checks fail **closed**: if path resolution throws, or the `os.walk()` over `data/raw/` raises an unexpected exception, the guard assumes the worse case and blocks — the comment says it plainly: "Cannot tell - assume present so the stricter branch applies (fail closed)." The top-level `if __name__ == "__main__":` block for the same file does the same at the outermost level: an unhandled crash writes a message and exits 2 (block), specifically because Claude Code treats a bare exit-1 crash as *non-blocking* — the read would otherwise silently proceed.

`run-guard.sh` makes the opposite call, and says so explicitly: if no suitable Python interpreter is found on the host at all, it exits 0 — allow — because "a hard block here would brick every tool call on a Python-less host, which is not the guard's job." The two decisions look contradictory side by side, but they're actually the same principle applied consistently: fail closed when the thing that broke is *inside the guard's own logic* on a host capable of running it; fail open when the thing that's missing is the guard's own ability to run at all, because bricking the entire tool surface is a worse outcome than an inert guard backed by the repo's other layers (the OS-level `permissions.deny` list, `.gitignore`, masking-at-source).

## 5. The engineering culture here is "measured live and dated," not "reasoned about in the abstract"

Nearly every fix cited above carries an exact date, an exact number, and an exact reproduction context, rather than a general justification — 2026-07-30/31 corporate reports with specific timings (51s, 1m31s, ~2 minutes), 2026-08-01 and 2026-08-07 audits with specific line-level root causes, three independently-measured incidents on 2026-08-10 alone (3816ms, 3555ms, and the raw-data walk). That's not decoration; it's because theoretically sound fixes in this codebase have repeatedly failed live and had to be replaced with something mechanically enforced instead. The clearest example is concurrent subagent dispatch: three separate prompt-only attempts each rephrased the instruction telling the model to dispatch reviewers concurrently — and each failed live, identically: dispatch went out sequentially every time despite the model's own narration claiming otherwise. The eventual fix replaced the prompt engineering entirely with Claude Code's `Workflow` tool, whose `parallel()` is a deterministic script construct with no per-turn judgement call involved — and even that mechanical fix needed two more live-tested patches before it actually worked end to end. The lesson the team has now paid for several times over: a plausible-sounding instruction to an LLM is not a control, and this codebase treats "verified live, with a timestamp and a number" as the actual bar for calling something fixed.

---

Put together, these five sections describe one underlying reality: cross-platform support, security-sensitive guarding, and AI-agent invocation are each individually well-understood problems, but their intersection is genuinely harder than any one of them alone — a fix for the Windows interpreter probe changes the process-spawn math, the process-spawn fix changes what a security guard's crash policy needs to preserve, and the security model only holds because the model itself is barred from editing it. Anyone building similar tooling should expect to pay this compounding cost, not just the sum of its parts.
