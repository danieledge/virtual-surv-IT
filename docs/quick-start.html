The Compliance Surveillance Engineering Team

A virtual delivery team for transaction-monitoring, trade-surveillance and comms-surveillance engineering. Morgan (the PM) coordinates 16 named specialists to build, test, review and hand over solutions, keeping the evidence for each step as it goes.

Always on · agents are blocked from reading data/raw/ Always on · code under review is not run without your consent Always on · all data is treated as PII/MNPI unless masked or synthetic

These guards are armed in every session, engaged or dormant. They are a real control against mistakes and prompt injection, not a sandbox against a determined attacker: see the safety model for what each one does and does not guarantee.

How this actually works

The whole mental model, no framework jargon required.

§1

An AI framework: one orchestrator, multiple subagents

Morgan orchestrates: planning, delegating. Mateo, Linh, Ravi and the rest are subagents, each with its own prompt, toolset and isolated context, seeing only its brief. That isolation is a feature: because specialists cannot see one another's reasoning, every review stays independent.

§2

Morgan coordinates the work rather than performing it herself

Morgan is the PM. She takes your request, decides which specialists the job actually needs, briefs them precisely, checks what comes back, and reports to you. You deal with Morgan directly; the rest of the team works behind the scenes.

§3

A loop is an iteration cycle, not a failure

A failed check does not stop the work, it becomes another iteration until the work meets the standard. Same idea as a PR review: flagged, fixed, re-reviewed. The AI term is evaluator-optimizer: one pass produces the work, an independent pass checks it against a named standard, and it ships once that pass clears.

§4

Talk to Morgan like you would a real PM

There is no command language to learn. Describe the outcome you want, in your own words. Morgan asks clarifying questions, flags anything unrealistic or risky, and checks in before anything material happens. Hand her context exactly as you would a colleague (a screenshot, a spec, an existing script) and she will work from it.

§5

📊 and 🧠 separate what was checked from what was reasoned

These are the tags you will see in every report, so they are worth knowing. 📊 marks something verified directly: a test run, a query executed, a metric taken from the data. 🧠 marks reasoning that goes beyond the evidence, still useful, but flagged so it is not read as fact. 📄 marks a value read straight from source code, with nothing run.

§6

Every piece of work gets its own folder

Each engagement lives in artifacts/<name>/: its brief, specs, code, tests, and a living START-HERE.md status page showing where it stands. Several can sit in the same project at once, each independent; one root index lists them all.

The words you will see

Enough AI vocabulary to follow what is happening, and no more. You will meet each of these in a normal engagement.

agent · subagent
A separate AI worker with its own instructions, tools and memory. Morgan is one; each specialist is another. They cannot see each other's thinking, only what is written down.
orchestrator
The agent that plans and delegates rather than doing the work. Here, that is Morgan. Also called a lead or router.
context
Everything the model can currently see: your messages, files it has read, results so far. It is finite, which is why each specialist gets a tight brief instead of the whole history.
compaction
What happens when a long conversation is summarised to fit. Anything that matters is written to disk precisely so it survives this.
tool call
The model doing something rather than saying something: reading a file, running a command. Every one passes a safety check first.
hook · guard
Code that runs before a tool call and can refuse it. This is what makes the safety rules enforcement rather than instructions the model could talk itself out of.
token
The unit models are billed and budgeted in, roughly a word-piece. Why the team uses the smallest set of specialists that fits rather than all 16.
hallucination
Confident output that is not grounded in anything real. The 📊 and 🧠 tags exist to make the difference visible instead of leaving you to guess.

Getting started

The team is dormant by default. Nothing below happens until you ask for it.

  1. /engage

    Type this to start anything. It's the one command to remember.

  2. Describe the work in plain English: a problem, a review, or something to build.
    e.g. "Build a wash-trading detection scenario for the equities desk."

    No need to name a specialist; Morgan routes it.

  3. Answer the menus Morgan opens (depth, scope, outcome). Pick an option, or just tell Morgan what is needed.
  4. Watch it work. Morgan briefs the specialists and reports back at each gate.

Best practices

  • Mention your materials: a screenshot, a spec, an existing script. Morgan works from what you hand her, and guesses less when you hand her more.
  • Say what "done" means: review only, or also fixed, or also handed over. Agreed before work starts beats renegotiated after.
  • Push back. Morgan is meant to be a sceptic rather than a yes-man, and so are you. If a finding looks thin, ask what the evidence actually was.
  • Check the tags. 📊 was measured, 🧠 was reasoned. If something important is 🧠, that's your cue to verify it before relying on it.
  • Do not hand it unmasked data. Use /prepare-data, or better, go synthetic. Pseudonymised is not anonymous.
  • It is a starting point. A proof of concept whose output is for real engineers and reviewers to check, not a replacement for them.
