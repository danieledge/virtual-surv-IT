# Release 0.33 - the team got harder to fool, and uses more of the platform (2026-07-29/30)

Everything in the 0.33.x cycle on one page, in plain language. Full technical change lists:
[`CHANGELOG.md`](../../CHANGELOG.md), entries `[0.33.0]` and `[0.33.1]`.

## The short version

We put the team's own workflow under a microscope and found that several of its safety
checks quietly switched off in exactly the situations they existed for. 0.33.0 fixes all
34 findings from that review, each one reproduced first and then fixed with a test that
proves it stays fixed. 0.33.1 then adopts the platform capabilities the team was leaving
unused, and fixes a live pain: PDFs handed to the team. Day to day you get: checks that
stay on, a close that has to earn its tick, sessions that pick up where they left off
without re-asking you things, one predictable place for every document, documents that
convert instead of confusing, and a progress panel while the team works.

## The checks stay on

Before this release, a few gaps meant the quality gate could fall silent just when it
mattered:

- If an engagement's index file was missing, the gate assumed everything was fine. Now the
  opposite: no readable status means the engagement is treated as still open and all the
  "not finished yet" protections stay armed.
- When the team ran as an installed plugin (rather than from its own repo), the end-of-turn
  check was silently doing nothing. It now works the same everywhere, and there is a test
  that runs it exactly the way an installed plugin does.
- A piece of delivered code could sneak past its "has this been QA'd?" check by pointing at
  QA paperwork that belonged to a different engagement in the same folder. Each piece of
  work now needs its own QA evidence, next to it.
- Files dropped loose into the artifacts folder used to be checked by nothing. New strays
  are now flagged; anything that was already there before this release is left alone.

## Closing an engagement now has to earn its tick

"Done" used to be something the team could simply declare. Now it is something the tooling
verifies:

- There is a new visible stage, 🔒 **closing**, between "in progress" and "closed". While
  it shows, the team is allowed to write its final documents, and if a session is
  interrupted mid-close, the next one is told to finish the job, never to delete the
  finished documents.
- The final flip to ✅ **closed** runs the entire mechanical quality checklist first, and
  refuses if anything is wrong. A closed engagement means the checks actually passed.
- If a close does happen by mistake, the list of work that was still outstanding is kept in
  the engagement's log, so nothing is lost.

## Sessions pick up where they left off

Long sessions get trimmed by the tool from time to time, and sometimes a session simply
dies. Everything important now lives on disk, so a fresh session:

- knows which engagement you were working on (it is recorded in the folder, not just in
  the conversation),
- remembers the answers you already gave at the start (the go-ahead, how you wanted
  findings handled, your data confirmation) and does not ask again,
- remembers how it was installed and which stage the work had reached.

One of these deserves its own line: **a No stays a No**. If you declined to let the team
run code, that refusal is now recorded and survives anything that happens to the
conversation. It is recorded in a way that can only ever say "asked" or "declined", never
"granted": permission to run code still exists in exactly one place, a marker file only you
can create.

## One home for every document

Every engagement now keeps everything it produces in its own folder,
`artifacts/<its-name>/`, with a fixed name for each kind of document. The operating guide
has a simple table of what goes where, and the tooling checks it. Two side effects you may
notice:

- The polished final review report only appears when an engagement is actually closing.
  While work is in progress you see numbered interim passes instead, so a half-done review
  can never be mistaken for the finished one.
- The START-HERE index in each folder is generated from the engagement's record, and the
  team can now tell if someone edited it by hand. If that happens, the edited copy is
  saved aside before the index is regenerated, so nothing typed is thrown away.

## The team's memory of your project is now checked

The team keeps one small "map" file per project it works on, its memory of how your code
is built. Until now, that map's claims about *when* and *against which version* something
was verified were decoration: nothing checked them. Now every entry's date and code
reference is validated, and a map that has fallen too far behind your repository gets
flagged as stale instead of being silently trusted. The quick low-ceremony engagement mode
also lost its permission to skip the map update at close.

## Straight talk about data preparation

`/prepare-data` now tells you clearly, every time, what it is: a convenience, not a
production anonymisation pipeline. It handles structured fields and simple patterns; it
will miss names hidden in running text. If your data is sensitive, mask or sanitise it
with your organisation's approved tools before it comes anywhere near the team, and prefer
fully synthetic data whenever you can.

## New in 0.33.1: documents, progress and resilience

- **Documents convert instead of confusing.** Hand the team a PDF, DOCX or spreadsheet and
  it routes through the bundled converter (`scripts/convert_file.py` - dependencies
  vendored, zero installs, built for locked-down corporate machines). A new `--layout`
  mode keeps PDF columns and tables readable. A new hook mechanically blocks the old
  failure (reading the binary bytes, PowerShell hand-parsing) during engagements and
  prints the exact command to run instead. Scanned pages are escalated to you, never
  guessed.
- **A progress panel while the team works.** The engagement's gates (brief, build, tests,
  review, QA, done-gate, close) appear in Claude Code's native task list, ticked as their
  evidence lands - a glanceable view that costs no console space.
- **A status line.** Once wired, the terminal's status bar shows "Morgan dormant" or the
  live engagement (name, status, phase), the project's docx/citations/model preferences,
  and session cost - rendered by a shell script, costing zero tokens.
- **Compaction stops losing the thread.** When a long session is compacted or resumed, a
  new SessionStart hook re-briefs the model: which engagement is active, and that the
  answers you already gave live on disk and are not to be re-asked (a consent No stays a
  No). Silent in every session that never engaged the team.
- **Mistakes surface one edit sooner.** A PostToolUse hook lints Python the moment a
  builder writes it (syntax always, ruff when installed) and feeds problems straight back,
  instead of waiting for the review gate.

## The people who are not people

A standing rule this release carries forward (it arrived in 0.32.0): every named team
member is an AI agent, and the documents make that impossible to miss. Any roster name
(Morgan, Amara, Layla and the rest) is marked 🤖 and attributed to **Virtual Surveillance
IT** the first time it appears, a legend sits under every sign-off table, and an agent
never shares a signature or approval line with a human, because only your approval carries
authority. This is checked mechanically, not left to good intentions, and so are invented
or wrongly-titled reviewer names.

## Upgrading

Nothing to do:

- **The hooks ship wired.** Every lifecycle hook in this cycle (the document-input
  redirect, the compaction/resume brief, the post-edit lint, alongside the existing
  guards, Stop gate and persona anchor) is already wired into the plugin's shipped hook
  files - installing or updating the plugin is enough. The `apply-*.sh` scripts in the
  repo are maintenance tools for re-wiring a hand-edited settings file; end users never
  need to run them.
- **One optional extra:** the status line is a per-machine setting, not a hook - if you
  want it, `bash scripts/apply-statusline.sh` from the clone wires it for this repo, and
  the README's Claude Code features section shows the one-line setting for any other
  project.
- Existing artifacts and old-style flat folders keep working; files already at the
  artifacts root were exempted once and stay exempt.
- You will start seeing the 🔒 closing stage, a few new check names in gate output, and
  two small bookkeeping files in the artifacts folder.

# 0.33.2 (2026-07-30) - Archiving and faster startups

One live report drove it: **in projects with a long engagement history, the team's
startup checks became slow** - every old engagement's artifacts were re-scanned on
every run, even though nothing had changed since they were verified at close.

Two answers, which work together:

## Archive anything with one marker file

Drop a file named `.archive` into any directory under `artifacts/` and every part of
the team ignores it from then on - the Definition-of-Done checker, the end-of-turn
gate, the engagement registry, the status line and the resume menu. Nothing is moved,
so links inside old reports keep working.

The tool-assisted way (Morgan runs this when you say "archive the old engagements"):

```
python -m scripts.engagement_state archive <slug>       # one engagement
python -m scripts.engagement_state archive --all-closed # every closed one
python -m scripts.engagement_state unarchive <slug>     # bring one back
```

The manual way: `touch artifacts/<anything>/.archive`. Both work; the tool also writes
a provenance line into the marker and updates the registry, which now shows a
collapsed `Archived: N` line instead of scanning those folders.

**The safeguard**: archiving an *open* engagement is refused (it would silence the
close gate). `--force` exists for genuinely abandoned work and records that fact in
the pack's log first. A bare hand-touched marker on an open pack shows up as an
`ARCHIVED-OPEN` warning on checker runs - visible, never silent.

## Closed engagements stop costing you (even unarchived)

When an engagement passes its close gate, the team now stores a lightweight
fingerprint of its files (names, sizes, timestamps - no content). On later scans, a
closed engagement whose fingerprint still matches is **skipped entirely**: the
verification it passed at close still stands. Touch any deliverable and the pack is
fully re-scanned again.

Engagements closed on earlier versions have no fingerprint yet, so they keep
full-scanning; the checker tells you when several are in that state and offers the
one-command fix (`archive --all-closed`).

## Also in this release

- **Windows status line fixed**: it previously fell back to a bare "🕶 virt-surv-IT"
  with no stats on Windows consoles (an encoding crash in the renderer); it now shows
  the full line everywhere.

## Compatibility

No migrations. Existing packs, flat layouts and registries keep working; the registry
regenerates itself on the next mutation. Nothing is archived automatically - the
markers are always your (or Morgan's, on your word) act.

# 0.33.3 (2026-07-30) - Optional docx export, mechanised audit findings, engage-startup fix

Three threads in one cycle: a document-format request, a live corporate-Windows report,
and a systematic audit of where the team relied on prompted recall for things a script
could check instead.

## Optional Word (.docx) export

Controlled documents (BRD, FSD, delivery report, etc.) always get `.md` + `.html`; now a
project can opt into a Word copy too, for reviewers who redline in Word rather than
Markdown. `.md` stays the one authored source - `.html` and `.docx` are both pure
derivations of it (the same sanitised HTML `render_html.py` already produces, walked into
a Word document by `render_docx.py`), so they can never drift from each other.

The preference (`.claude/team-preferences.json`) is project-wide, alongside a second
preference for regulatory citations (on by default; a project can turn them off if it
isn't operating in a regulated context, or if citations came back wrong and you'd rather
they be optional). Two ways to change either: the installer's re-runnable "Project
preferences" menu, or the new **`/preferences`** skill - Morgan can read and write the
file directly on your word, no consent gate, no engagement needed.

## Engage startup slowness on a corporate Windows box

A live report - "/engage takes several minutes" - traced to two causes, one of them
reproducible even on a fast dev machine once found:

- an unbounded `find` in the plugin-root discovery fallback, walking every file of every
  installed plugin just to locate one file;
- the safety-guard launcher re-executing `python3`/`python`/`py` to version-check them on
  **every single hook fire** - five hooks per Bash call, all session long. On a Windows
  box where `python3.exe` is the Microsoft Store execution-alias stub, that repeated
  version-check hang was the whole story.

Both are fixed: the search is bounded and scoped to this plugin's identity, and the guard
launcher now caches the first working interpreter (the installer pre-seeds it at
project-enable time, so even the very first hook call never pays the discovery cost).
While in there: the installer itself now self-relocates before syncing, so running it from
inside the very clone it's about to update no longer risks a Windows file-lock failure.

## Eight mechanised audit findings

A structured review asked: where does the team rely on the model reliably remembering or
re-deriving something a script could just check? Eight answers landed, each with tests
and, where the failure had already happened live, a citation of the incident:

- the resume-vs-new engagement menu is computed, not re-derived from text (closed two
  live defects from the same day - a menu showing only one open engagement when several
  existed, and a session folding new work into the wrong open pack);
- a review report missing or leaving empty its mandatory Developer-guidance section is
  now caught mechanically, closing a gap where the documentation *claimed* this was
  already checked and nothing was;
- a rendered review report that has drifted from its source findings pack (a finding
  added, removed, or its disposition changed after the last render) is now caught;
- a subagent return clearly over the condensed-return token budget gets feedback instead
  of silently ballooning the orchestrator's context;
- the two LOCKED question-tool menus (review depth/performance/fix-cycle, artifact
  packaging) are now guarded against the exact drift class that got them locked in the
  first place - before a malformed version ever reaches you, not after.

Two things were deliberately left as judgement calls rather than mechanised: sweeping a
struck citation from every document (nothing in the codebase currently marks a citation
as struck in a detectable way - a checker would be guessing at a convention that doesn't
exist), and verifying "late-cycle changes propagated" into every touched document (this
needs understanding *what* changed and *why*, which is genuinely a human judgement, not a
fact a script can extract).

## Compatibility

No migrations. Both new document/citation preferences default to today's existing
behaviour (`.md` + `.html` only, citations on) - nothing changes for an existing project
until you opt in.

# 0.33.4 (2026-07-30) - Task-list gate panel, backed by a nudge

The operating guide claims delivery-phase engagements show their gates (brief → build →
tests → review → QA → DoD gate → close) in Claude Code's native task list. Checking that
claim against every kept live eval transcript found zero genuine TodoWrite calls - a real
capability, described in prose, never actually nudged into happening.

TodoWrite can't be driven by a script (it's model-invoked, no external caller) and its
live content isn't observable from outside the running turn - so this can't become a
mechanical check the way the 0.33.3 audit findings did. What's achievable instead: a
Stop-hook nudge, firing once a gated engagement's phase reaches delivery, reminding
Morgan to seed the panel. It self-suppresses - via a marker Morgan logs once the panel
reflects the gates - without the hook itself ever writing engagement state, keeping every
hook in this codebase read-only.

## Compatibility

No migrations. The nudge only fires during a live, gated engagement once delivery phase
is reached - a dormant session or one that never reaches delivery never sees it.

# 0.33.5 (2026-07-31) - Corporate Windows hardening: probe, statusline, engagement_state fixes

A user ran 0.33.4 on a real corporate Windows 11 / Python 3.13 box and reported eleven
issues, most diagnosed precisely enough to fix directly. Three shared one root shape -
something *looked* like it existed or worked, but a check that only confirmed presence
(not that the thing actually ran) let it fail silently downstream:

- the `/engage` probe's `python3`/`python`/`py` fallback chain crashed on `print()` under
  a cp1252 console codepage (the report's emoji), and the whole compound's `2>/dev/null`
  hid it completely - the probe just looked like it did nothing;
- `statusline.sh` resolved the interpreter with `command -v`, which only checks PATH
  existence - true for the Windows Store execution-alias stub, which exists on PATH but
  exits 49 without running, so the line silently degraded to the static fallback glyph
  even with a real interpreter available right behind it;
- `engagement_state.py`'s internal `render_html` import assumed the `scripts` package
  was on `sys.path`, true under `-m` invocation but false under plugin-mode path
  invocation - every mutation quietly skipped its `.html` render, which cascaded into
  `check_artifacts`'s `REGISTRY-HTML-STALE` finding re-firing on every single mutation
  with no way to clear it.

The remaining issues were rough edges rather than silent failures: `--slug`/`--dir` only
worked before the subcommand on `engagement_state.py` (an argparse ordering quirk with no
error message pointing at the fix); `archive --force` couldn't exclude a legacy
directory with no `engagement-state.json`, only a real closed pack; `render` exited 0
even when its `.html` sibling was skipped; the task-panel Stop-hook nudge fired with no
identifying detail about which engagement triggered it; and there was no `show`
subcommand for inspecting one engagement's state without opening the JSON by hand or
risking `validate`'s exit-1-on-findings behaviour.

Full list in `CHANGELOG.md`. Every fix was verified end-to-end against the actual
plugin-mode invocation path (direct script path, no `PYTHONPATH`, no `scripts` package
on `sys.path`) that the corporate report ran under, not just the `-m` path this repo's
own test suite exercises by default.

## Compatibility

No migrations. `--slug`/`--dir` accept the same values as before, just in more
positions; `archive --force` and `render`'s exit code are additive/stricter, not
breaking, for any script already treating a `render` exit 0 as "html included".

# 0.33.6 (2026-08-01) - Framework audit remediation: guard escapes closed, traceability gated, eval numbers made readable

A full audit of the framework (safety guards, agent and skill layers, eval harness, and the AI
concepts underneath) and the remediation of everything it found, across ten workstreams.

## The finding that framed the rest

The most serious defect was not a missing control. It was a **silent** one.

The execution guard had drifted from its staged copy, missing three entries from the team-script
allow-list, one of them the probe that `/engage` runs at step 0. In plugin mode, where skills
invoke bundled scripts by path, that meant the product asked users for execution consent to run
its own front door, which the handbook explicitly forbids.

The test that should have caught it called `pytest.skip()` when the staged fix was unapplied, so
the suite reported green throughout. The regression net went quiet at exactly the moment it had
something to say.

That is the same shape as the story this project opens with: FCA Market Watch 79, a feed that
never fired for three years, where a working system and a broken one both looked like "no alerts
today". Pending guard work now **fails** the suite rather than skipping, across every staged file
and all five hook event families.

## Escapes closed in the safety guards

`.git/config` and `git config core.hooksPath` were a consent-equivalent execution path: setting a
hooks directory, an external diff or merge driver, or an alias handed the next `git commit` or
`git diff` arbitrary execution without ever writing the consent marker. The "the model cannot
grant itself execution consent" property held technically while its purpose was defeated.

The raw-data guard gained three pieces of coverage: `WebFetch` with a `file://` URL (which
addresses the local filesystem and is a live tool, so a gap previously rated architectural was
live), searches rooted at a parent of the protected directory or at no path at all (which walk
into it while naming a path that does not resolve under it), and a defence-in-depth scan for read
tools outside the known set. The parent-rooted check fires only when raw records actually exist on
disk, so a fresh clone or a synthetic-only project keeps normal repo-wide search.

Both were verified against the live guards, not only the staged copies.

## Claims turned into mechanisms

The traceability spine (requirement to spec to code to test to obligation) was the most-marketed
guarantee in the product and had no validating code at all; the RTM template had specified a
bidirectional coverage check that was never built. It is now a real validator, gated through the
artifact checker. Absence of an RTM is not a finding, so existing engagements are unaffected.

The release gate parses a verdict rather than checking that a baseline file exists. The eval judge
reads the deliverables instead of a directory listing plus the PM's own account of its own work.

## The 35% that was not what it looked like

The team's self-test previously reported a **35%** pass rate. That number was a floor depressed by
runs that never finished, not a measure of team quality: a timeout or a dropped session was scored
the same way as the team answering badly, so a run that produced no answer at all counted against
the result.

Runs are now classified pass, fail or **unscorable**, so an infrastructure death is never counted
as a quality failure, and the share of unscorable runs is tracked separately as a health signal for
the test harness itself. On the same history the corrected figure is **47%**.

## What this release deliberately did not do

- **No decision on the persona layer.** ADR-012 states the costs and the options and leaves the
  ruling to the human. Inaction defaults to keeping the named roster, and that is itself a
  decision.
- **No committed eval baseline was back-filled** to make the stricter release gate pass. The gate
  correctly refuses to promote until this release has a baseline of its own.
- **`/engage` was cut by 19.4%, not the 40% planned.** Going further meant relocating the
  go-ahead gate, blocked-state truthfulness and state-persistence rules, the most incident-prone
  surface in the product. What remains is operative rules rather than accreted prose.

## Carried forward

The test harness's per-case time budget looks too tight for the longest cases: diagnosed during
this cycle, not confirmed and not fixed.

One finding raised during the audit was later **retracted** on closer analysis, when conditioning
the data on whether a run had actually finished changed the conclusion. It is recorded rather than
quietly dropped, because an audit that removes its own wrong conclusions is exactly the tidy
narrative this project warns about.

## Compatibility

No migrations. The two guard changes are promoted by the human via
`scripts/apply-guard-git-config.sh` and `scripts/apply-guard-raw-coverage.sh`; both were applied
and verified in this cycle. Existing engagements without an RTM see no new findings.

# 0.33.7 (2026-08-03) - Windows-detection, a missed status word, and a docs pass from a live session

Three defects found by watching a real corporate-Windows session hit friction, none of them the
Windows-encoding class of bug this cycle had already fixed once.

The step-0 probe never told the model whether it was running on Windows -
`.claude/skills/engage/references/safety-gates.md` already said to show the PowerShell
exec-consent form alongside the `!` form there, but the model
had to infer Windows-ness from soft context at the exact moment it needed to remember that rule,
and on a live host it gave the `!` form alone. The probe now reports `OS=Windows|POSIX` as a
plain fact, the same reasoning `INTERPRETER=` already exists for: don't make the model infer
something it can just be told.

A closed delivery report could still read `Status \`Pending\`` with the mechanical DoD gate
silent about it, because the check that closes out document-control status fields only ever
matched draft/in review/in progress - "pending" was never in the pattern, even though no
template's placeholder uses that word, so it was always author-written scaffolding text that
never got updated. And the locked review-menu construction and the intake gate's own question
batch used near-identical "batch these in one screen" phrasing with nothing stating they are two
separate calls at two different points in the flow, which let a live session carry the intake
gate's `Execution` header into the review-menu call - `locked_menu_guard.py` caught it and the
model recovered in the same turn, but the friction was real.

Alongside the fixes: a one-page quick-start reference as a PDF (GitHub never renders `.html`
inline; a PDF renders directly in its file viewer), a "what Morgan cannot do" section stating the
boundaries as plainly as the capabilities, the engagement-flow poster's stale README caption
fixed (the poster itself was already current, the caption describing it was not), and the
installer's default channel switched from `main` to `dev` for this fast-moving PoC phase, where
promoting to `main` is eval-gated and costs real API tokens.

## Compatibility

No migrations. `OS=` is a new, additive probe field; nothing that read the probe's prior output
breaks. The `_STALE_DOCSTATUS_RE` change only ever adds a new finding on a document that says
"Pending" and means it - a legitimate `Status \`Pending human sign-off\`` still passes.
